# Ponytail audit — 2026-10-15

HEAD `f766607`. Read-only: no code changed by this audit.

## What this repo does

A marketing site and lead-capture app for a one-person AI consultancy. It is a
Next.js 16 App Router app on Firebase Hosting, with an SSR Cloud Function for
the dynamic routes. Nine API routes take form submissions, write them to
Firestore, and send email through Resend. Two tracks are sold: 1:1 coaching
and done-for-you builds.

**Load assumed:** public marketing traffic, plus a few form submissions a day
and one daily cron job. Concurrency is low. But the API routes accept
unauthenticated input from anyone on the internet, so I judged the rate
limiter and the admin route against a hostile sender, not a friendly one.

**Not checked:** the visual design (I cannot see rendered output), the
Firebase project's live security rules and IAM, Resend account limits, and the
`mirrors/` tooling internals.

## Must fix

### 1. The rate limiter does not limit, and its memory grows forever
`src/lib/email/rate-limit.ts:6, :19-37, :39-43`

- **What this is:** A small in-memory counter that blocks IP addresses which
  send too many requests. Every submission route depends on it.
- **Problem:** The bucket key is the raw first value of the `x-forwarded-for`
  header, which the caller supplies. Nothing ever removes old entries from the
  `Map`. Measured in a probe: 500 calls with 500 distinct header values at a
  limit of 5 → **500 allowed**. The same key 6 times → blocked at 6. A single
  forged header per request defeats it. Separately, `grep` finds zero
  `delete`/`clear`/`evict` in the file, so every distinct value is kept for the
  life of the process.
- **Fix:** Take the client IP from the platform, not the client header. Prune
  expired entries when the `Map` passes a bound.
- **If we skip it:** Each submission endpoint sends two real emails, so
  unlimited requests mean Resend quota and bill, plus a flooded inbox. The
  memory growth needs no attacker at all and ends in an OOM.

### 2. The admin session cookie never expires on the server
`src/lib/admin-session.ts:6-11, :13-24, :34`

- **What this is:** The login token for the private admin pages.
- **Problem:** The token is a constant, `HMAC(secret, password)`. No issue time,
  no nonce. Checking only compares it for equality, so its age is never
  examined. The 8-hour `maxAge` is a browser hint and nothing more.
- **Fix:** Sign a timestamp into the token and reject it when it is older than
  the session length.
- **If we skip it:** A cookie copied today still works in eight months, and
  returns client names, emails and full intake answers from
  `/api/admin/cases`. The only revocation is changing the password.

### 3. The admin password is compared byte by byte
`src/app/api/admin/verify/route.ts:45` compared with `src/lib/admin-session.ts:20`

- **What this is:** The password check on the admin login.
- **Problem:** The password uses `===`, which stops at the first differing
  byte, so the reply time varies with the length of the matching prefix. The
  cookie check two files away already does this correctly with
  `timingSafeEqual`. The same rule is applied two different ways.
- **Fix:** Use `timingSafeEqual` on the two values, as the cookie check does.
- **If we skip it:** Finding 1 removes the rate limit that was the main
  obstacle, leaving a byte-at-a-time recovery of the password that guards all
  client PII.

### 4. Contact messages are never saved
`src/app/api/contact/route.ts:4-9`, `src/lib/submission-pipeline.ts:248-251`

- **What this is:** The contact form in the closing section.
- **Problem:** The route injects a do-nothing store, and `submitContact` has no
  store parameter at all, so it could not save even if asked. The email is the
  only copy.
- **Fix:** Give the contact path a real collection, and write before sending.
- **If we skip it:** A visitor's message arrives during a Resend outage, the
  route returns 500, and the message is gone. Contact enquiries are the
  highest-intent leads and the only ones with no durable record.

### 5. Identity intake emails raw, unbounded input
`src/lib/paid-case-intake.ts:218-233` against `:151-170`

- **What this is:** The owner notification email sent when someone submits a
  paid intake form.
- **Problem:** The audit notification uses the cleaned payload; the identity
  notification uses the raw request fields. Measured: a 50,000-character
  `notes` field stores 1,000 characters but builds a 53,328-character email
  containing all 50,000. The same input on the audit path produces 5,998
  characters.
- **Fix:** Read `payload.intake.*` in the identity notification, matching audit.
  About three lines.
- **If we skip it:** Email size is unbounded on that endpoint, and the saved
  record and the inbox disagree, so the inbox becomes the only copy of the text.

### 6. An email failure returns 500 on a submission that already succeeded
`src/lib/submission-pipeline.ts:178-190, :229-241, :272-289`, `src/lib/paid-case.ts:105-117`

- **What this is:** The order in which a submission is saved, emailed to the
  visitor, and emailed to the owner.
- **Problem:** Whether an email failure aborts the whole request differs
  between pipelines, and even inside one. On the assessment path the visitor
  email succeeds, the owner notification then throws, and the route returns
  500. The lead is already stored and the visitor already has an email. The
  contact path treats the same situation as non-fatal.
- **Fix:** Pick one rule — visitor email fatal, owner notification best-effort —
  and wrap the owner sends in `try`/`catch`, as contact already does.
- **If we skip it:** The visitor sees a failure, submits again, and creates a
  second lead and a second email. Meanwhile Alex is never told his own
  notification failed.

## Should fix

### 7. The nudge chases clients who have already booked
`src/app/api/cron/nudge/route.ts:29-33`, `src/lib/cron/nudge-overdue.ts:35`, `src/lib/audit/case.ts:62`

- **What this is:** A day-3 email to people who requested a roadmap but did not
  book, deliberately skipping anyone who has.
- **Problem:** Nothing in the codebase ever writes `booking.scheduledAt`, and
  `status` never leaves `submitted`. The guard is real but has no writer.
- **Fix:** Add the writer, or delete the guard and the unused state modules so
  the code stops implying a protection it does not have.
- **If we skip it:** A client who booked from the confirmation email still gets
  "Still want the roadmap?" three days later — the exact dark pattern that
  module's own header claims to avoid.

### 8. The nudge re-reads every case it has ever nudged
`src/app/api/cron/nudge/route.ts:29-33`

- **What this is:** The query that finds cases needing a nudge.
- **Problem:** It filters on `status` and `createdAt` only. `nudgedAt` is
  filtered in memory after the fetch, so a nudged case matches every future run
  forever.
- **Fix:** Set `status: 'nudged'` when stamping, so the query excludes it.
- **If we skip it:** At ten cases a day for a year, each run reads about 3,000
  documents to send roughly zero emails. Firestore bills per read, and the run
  eventually times out before reaching cases that do need a nudge.

### 9. Two overlapping cron runs send two nudges
`src/app/api/cron/nudge/route.ts:29-33, :54-64`

- **What this is:** The send-and-stamp loop.
- **Problem:** It reads, then sends, then stamps — with no transaction. Two
  overlapping runs both read the same documents as un-nudged and both send.
- **Fix:** Claim each document in a transaction before sending.
- **If we skip it:** Any retry that overlaps the schedule sends a duplicate
  email. So does any failure of the stamp write, because the loop aborts and
  the next run re-sends.

### 10. The Substack route cancels its timeout before reading the body
`src/app/api/substack/route.ts:6-18`

- **What this is:** The route that fetches the newsletter feed for the homepage.
- **Problem:** `clearTimeout` runs at line 14, right after `fetch` resolves, but
  the body is read at line 18. The 5-second abort therefore covers the headers
  only.
- **Fix:** Move `clearTimeout` after the body read, or into a `finally`.
- **If we skip it:** An upstream that sends headers then stalls holds the
  request until the platform kills it. A few of those exhaust function
  concurrency.

### 11. Nothing tests the auth, money or write branches
No test file imports `checkRateLimit`, `isValidAdminSessionToken`,
`isValidEmail` or `sanitizeEmailHeaderValue`. There is no test for
`cron/nudge/route.ts` or `admin/verify/route.ts`.

- **What this is:** 30 test files, 165 tests, all passing — but the risky
  branches are not among them.
- **Problem:** The rate limiter is exercised once, indirectly, with a limit of
  1. The cron secret check, its 401 and its send loop are untested, which is
  why findings 1, 8 and 9 survived. The pipeline tests contain no
  `mockRejectedValue`, which is why finding 6 survived.
- **Fix:** Add tests for the cron route and for a first-send failure. Then
  `email/validation.ts`, whose `escapeHtml` and header-injection guards are
  entirely unasserted.
- **If we skip it:** The bypass, the permanent session and the duplicate-send
  path can regress unnoticed.

### 12. Dead weight: about 11.4 MB of tracked files nothing references
`mirrors/` (8.4 MB, 29 files), `graphify-out/` (828 KB, 117 files),
`preview-hero.png` (2.2 MB), `context.md`, `autoresearch-results.tsv`,
`AUDIT_REPORT.md`, `GEO-AUDIT-RE-2026-06-19.md`,
`SEO-GEO-AUDIT-2026-06-19.md`

- **What this is:** Tracked files with zero references anywhere in the tree.
- **Problem:** Every one was checked by grepping its basename and its alias
  across source, config, CI and docs. One is worse than clutter: `context.md`
  and the canonical `CONTEXT.md` differ only in case, so on macOS or Windows
  one silently clobbers the other.
- **Fix:** Delete them. `context.md` first, because of the collision.
- **If we skip it:** The repo keeps carrying 11 MB, and a case-insensitive
  checkout can lose the canonical domain document.

### 13. Four dependencies are installed and never imported
`react-day-picker`, `react-hook-form`, `@radix-ui/react-tabs`,
`@radix-ui/react-toast`

- **What this is:** Packages in `package.json` with no import anywhere.
- **Problem:** All four are leftovers from a component library scaffold. No
  `calendar.tsx`, `form.tsx`, `tabs.tsx` or `toast.tsx` exists. `@opentelemetry/api`
  also shows zero importers but is an optional peer of Next — leave it.
- **Fix:** Remove the four.
- **If we skip it:** Four more packages to install on every build, and four more
  to audit for vulnerabilities.

### 14. Leftovers in `scripts/` and one unused component
`scripts/cleanup-canaries.mjs`, `scripts/cleanup-canaries-curl.sh`,
`scripts/_check-clamp.mjs`, `src/components/ui/badge.tsx`

- **What this is:** Two scripts that do the same one-time cleanup job by two
  different transports, one one-off CSS probe, and the only unused UI component.
- **Problem:** Both canary scripts are zero-reference and neither job needs
  running again. `_check-clamp.mjs` hardcodes a browser build (`chromium-1228`)
  that is not installed, so it cannot run.
- **Fix:** Delete all four.
- **If we skip it:** Small, but each is something a reader must open and
  dismiss.

### 15. The Docker build pulls in the whole tree
`Dockerfile`, no `.dockerignore`

- **What this is:** The container build for anyone who uses the Dockerfile.
- **Problem:** It runs `COPY . .` after `npm ci`, so the context includes
  `node_modules`, `.next`, `mirrors/` and `preview-hero.png`.
- **Fix:** Add a `.dockerignore`.
- **If we skip it:** Nothing on the live site, because the real deploy is
  Firebase. Only the Docker path is affected.

`.bg-shell/manifest.json`

- **What this is:** A tool config committed before the ignore rule was added.
- **Problem:** A ignore rule does not untrack a file that is already tracked.
- **Fix:** `git rm --cached` it.
- **If we skip it:** The rule and the tree disagree.

### 19. A barrel module that its own comment says not to use
`src/lib/email-utils.ts`

- **What this is:** A re-export layer over `email/validation.ts`,

- **Fix:** Either delete the advice or move the callers.

## Verdict

**Fix 1, 2 and 4 first.** Each is small, each is a real hole, and together they
are the difference between an app that holds up to a hostile sender and one
that does not. Finding 6 is the one your visitors will actually feel, because
it shows them an error after their submission worked. Nothing in the "must fix"
group needs a new dependency or a new layer.

**Lean: about -11.4 MB and -4 dependencies possible**, plus roughly 200 lines
from findings 14, 16, 17, 18 and 19.

**Not checked:** rendered layout and visual design; the live Firebase security
rules and IAM; Resend plan limits; the two docs under `mirrors/`; and whether
anything outside this repo reads the files listed in finding 12.
